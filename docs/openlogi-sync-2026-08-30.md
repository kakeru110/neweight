**SとMのどちらかで商品登録またはピッキングを取り違えている**可能性。
`Two of a kind Sweat For Dog` にも同じパターン（XS+5 / L+5 に対し S-5 / S-4）があります。

### 型2: 同一商品の全バリアントが一律にズレている → 同期が途中で止まった疑い
`Brittany Spaniel Short Sleeve Tee For Kids` は **12バリアント全部**が Shopify のほうが +2〜+3。
出荷はされたが Shopify 側の在庫が減っていない、という挙動に見えます。

### 型3: 多数のSKUで一律 +1
ドッグ用・キッズ用を中心に +1 が40件以上。型2と同じ原因の可能性。

> **どの型も「Shopifyのほうが多い」＝在庫がないのに売れる方向**です。

## OpenLogi APIについて

### APIはあります

| 項目 | 内容 |
|---|---|
| 形式 | REST / JSON |
| ドキュメント | https://api.openlogi.com/doc/api.html |
| 在庫取得 | `GET /items?stock=1`（個別は `GET /items/{id}?stock=1`） |
| 認証 | `Authorization: Bearer <アクセストークン>`。トークンに有効期限なし |
| レート制限 | **60リクエスト / 分**。超過で HTTP 429 |
| 費用 | API自体は無料（オープンロジの物流サービス契約が前提） |

### ただし「繋げた方がよいか」の答えは No（今は不要）

**理由1: すでに繋がっています。**
Shopifyに `Open Logi 倉庫` というロケーションが存在し、1,018点が乗っています。
オープンロジのShopifyアプリによる連携は**既に稼働中**です。
つまり課題は「繋ぐこと」ではなく、**繋がっているのにドリフトしていること**。
APIを新たに追加しても、この原因は解決しません。

**理由2: APIを足して得られるのは「照合の自動化」だけ。**
現状それは、月1回オープンロジの管理画面から配送可在庫のExcelを落として渡してもらえば、
同じレポートを生成できます。商品34点・SKU171件というこの規模で、
アクセストークンの保管とスクリプトの常駐運用を抱えるコストは、正直見合いません。

### APIを繋ぐ価値が出るのはこういうとき

- 照合を**週次以上の頻度**で回したくなった
- 出荷実績を売上分析に自動でひも付けたくなった
- 商品数・SKU数が数倍に増えた

そのときは、このリポジトリに突合スクリプトを置き、
トークンを環境変数で渡す形にすれば実装できます。**いま作る必要はありません。**

## だから次にやるべきはこれ

**APIではなく、既存のオープンロジShopifyアプリの設定を点検すること。**

1. アプリの連携が有効か、エラーで止まっていないか（オープンロジ管理画面の連携ログ）
2. 「入庫実績連携」「出庫実績連携」の設定がどうなっているか
3. `原田家` ロケーションを在庫計算に含める運用でよいのか
4. 型1（S/Mの入れ替わり）が実物レベルで起きていないか、倉庫に確認
